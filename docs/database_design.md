# Проектирование базы данных Media Storage

## 1. Область и ограничения MVP

Данный проект сейчас представляет собой frontend-MVP без серверной части. В текущем интерфейсе есть три ключевые сущности:

- медиафайл;
- коллекция пользователей;
- связь между коллекцией и медиафайлом.

Сценарии из интерфейса и mock-данных показывают, что пользователь:

- видит библиотеку файлов с типом image, video, audio;
- создаёт свои коллекции;
- добавляет файл в коллекцию один раз; повторное добавление запрещено;
- удаляет файл из коллекции и удаляет саму коллекцию;
- не должен видеть записи других пользователей.

Поскольку binary-файлы хранятся в Supabase Storage, в PostgreSQL сохраняются метаданные, путь к объекту в bucket и служебная информация для выборок, поиска и RLS.

---

## 2. Сущности и их соответствие текущей модели

### 2.1 MediaItem

Текущая frontend-модель содержит следующие поля:

- id
- title
- type
- size
- createdAt
- previewUrl
- duration (опционально)
- tags

Это соответствует реляционной таблице media_items.

### 2.2 MediaCollection

Текущая frontend-модель содержит:

- id
- name
- description
- mediaIds

В реляционной схеме эта структура хранится как отдельная таблица collections, а связи между коллекцией и файлами — в таблице collection_items.

### 2.3 Связь между коллекцией и файлами

Текущая модель коллекции хранит массив mediaIds. В PostgreSQL это лучше выразить через отдельную таблицу collection_items, чтобы:

- запретить дубликаты одной и той же записи в коллекции;
- быстро получать список файлов коллекции и обратные связи по файлу;
- обеспечить проверку владельца коллекции и файла на уровне базы.

## 3. Схема базы данных

### 3.1 Таблица media_items

Назначение:

- хранение метаданных всех файлов пользователя;
- привязка файла к владельцу;
- поддержка фильтрации по типу, поиску по названию и тегам;
- хранение пути к объекту в Supabase Storage.

Поля:

| Поле | Тип | Описание | Ограничения |
| --- | --- | --- | --- |
| id | uuid | идентификатор файла | PRIMARY KEY, default gen_random_uuid() |
| owner_id | uuid | владелец файла | NOT NULL, FK auth.users(id), ON DELETE CASCADE |
| title | text | название файла | NOT NULL, длина > 0 |
| type | public.media_type | тип файла | NOT NULL, CHECK по enum image/video/audio |
| size | bigint | размер в байтах | NOT NULL, CHECK size >= 0 |
| file_path | text | путь к объекту в Storage | NOT NULL, UNIQUE, длина > 0 |
| preview_url | text | URL превью или маршрутизируемый путь | NOT NULL, длина > 0 |
| duration_seconds | integer | длительность в секундах | NULL, CHECK >= 0 |
| tags | text[] | список тегов | NOT NULL, default '{}' |
| created_at | timestamptz | время загрузки | NOT NULL, default now() |

Почему duration_seconds, а не строка формата mm:ss:

- в SQL удобнее хранить длительность в числовом виде;
- приложение может формировать строку display-формата на уровне frontend;
- это уменьшает риск ошибок сравнения и сортировки.

### 3.2 Таблица collections

Назначение:

- хранение пользовательских подборок;
- привязка коллекции к конкретному владельцу;
- поиск и сортировка коллекций по имени и дате создания.

Поля:

| Поле | Тип | Описание | Ограничения |
| --- | --- | --- | --- |
| id | uuid | идентификатор коллекции | PRIMARY KEY, default gen_random_uuid() |
| owner_id | uuid | владелец коллекции | NOT NULL, FK auth.users(id), ON DELETE CASCADE |
| name | text | название коллекции | NOT NULL, длина > 0 |
| description | text | описание | NOT NULL, default '' |
| created_at | timestamptz | время создания | NOT NULL, default now() |

### 3.3 Таблица collection_items

Назначение:

- хранение связей между коллекциями и медиафайлами;
- запрет дубликатов внутри одной коллекции;
- быстрый подсчёт количества файлов в коллекции.

Поля:

| Поле | Тип | Описание | Ограничения |
| --- | --- | --- | --- |
| id | uuid | идентификатор связи | PRIMARY KEY, default gen_random_uuid() |
| collection_id | uuid | коллекция | NOT NULL, FK collections(id) ON DELETE CASCADE |
| media_item_id | uuid | медиафайл | NOT NULL, FK media_items(id) ON DELETE CASCADE |
| created_at | timestamptz | время добавления | NOT NULL, default now() |

Дополнительные ограничения:

- UNIQUE (collection_id, media_item_id) — запрет повторного добавления одного и того же файла в одну коллекцию.

---

## 4. Ограничения и индексы

### 4.1 media_items

Ограничения:

- type IN ('image', 'video', 'audio');
- size >= 0;
- duration_seconds IS NULL OR duration_seconds >= 0;
- title, file_path, preview_url не пустые строки;
- file_path UNIQUE внутри всей таблицы.

Индексы:

- (owner_id, created_at DESC) — список файлов пользователя по времени;
- (owner_id, type, created_at DESC) — фильтрация по типу и сортировка по дате;
- (owner_id, title) — ускорение поиска по названию;
- GIN(tags) — поиск по тегам и быстрый фильтр по массивам тегов.

### 4.2 collections

Ограничения:

- name не пустой;
- description может быть пустым, но хранится как text.

Индексы:

- (owner_id, created_at DESC) — список коллекций владельца;
- (owner_id, name) — поиск и сортировка по имени.

### 4.3 collection_items

Ограничения:

- UNIQUE(collection_id, media_item_id);
- каждая запись связана с существующей коллекцией и существующим файлом.

Индексы:

- collection_id — быстрый просмотр содержимого коллекции;
- media_item_id — быстрый поиск всех коллекций, в которых участвует файл;
- уникальное ограничение уже обеспечивает защиту от дубликатов.

## 5. RLS-стратегия

### 5.1 Включение RLS

RLS включается для всех трёх таблиц:

- public.media_items
- public.collections
- public.collection_items

Это обязательное условие, потому что frontend-валидация и клиентский код не являются защитой от прямых REST или SQL-запросов.

### 5.2 Правила доступа

#### media_items

- SELECT: только собственные записи user_id = auth.uid();
- INSERT: только со своим owner_id = auth.uid();
- UPDATE: только собственные записи и owner_id не меняется;
- DELETE: только собственные записи.

#### collections

- SELECT: только собственные записи по owner_id = auth.uid();
- INSERT: owner_id устанавливается автоматически из auth.uid();
- UPDATE: только собственные коллекции;
- DELETE: только собственные коллекции.

#### collection_items

- SELECT: только для коллекций текущего пользователя;
- INSERT: только если коллекция принадлежит текущему пользователю и файл тоже принадлежит этому пользователю;
- DELETE: только если коллекция принадлежит текущему пользователю;
- UPDATE: не требуется для MVP и не открывается.

Это закрывает сценарий, где злоумышленник пытается добавить чужой файл в собственную коллекцию или добавить свой файл в чужую коллекцию. На уровне RLS проверяется и принадлежность коллекции, и принадлежность media_item.

## 6. Миграция

Миграция находится в файле:

- supabase/migrations/20261015_000001_create_media_storage_schema.sql

Она содержит:

- создание enum media_type;
- создание таблиц media_items, collections, collection_items;
- ограничения NOT NULL, CHECK, UNIQUE, FK;
- индексы для поиска и фильтрации;
- включение RLS;
- политики доступа по владельцу.

Для применения в проекте требуется:

1. инициализированный Supabase проект и локальная настройка Supabase CLI;
2. запуск команды supabase init (если проект ещё не настроен);
3. размещение SQL-файла в каталоге supabase/migrations;
4. применение миграции командой supabase db push или supabase migration up.

В этом репозитории CLI ещё не настроен, поэтому SQL подготовлен как готовый шаблон под дальнейшее применение, но не запускался на удалённом проекте.

## 7. Обоснование принятых решений

1. Использована модель owner_id в каждой таблице.
   - Это соответствует требованиям изоляции пользовательских данных.
   - Позволяет выполнять RLS без дополнительных ролей.

2. collection_items вынесен в отдельную таблицу.
   - Это нормальная форма для многих ко многим.
   - Позволяет запретить дубликаты и пересчитывать количество файлов без хранения массивов в PostgreSQL.

3. Файлы и метаданные разделены по ответственности.
   - Хранение бинарников — в Supabase Storage.
   - Метаданные и ссылки — в PostgreSQL.
   - Это соответствует требованиям проекта и упрощает управление доступом.

4. Для типа файла выбран enum media_type.
   - Это уменьшает вероятность неправильных значений.
   - В приложении допустимы только image, video, audio.

5. Для duration использовано numeric seconds rather than raw string.
   - Это более корректно для SQL и дальнейших фильтров.
   - Для UI можно удобно форматировать обратно в mm:ss.

## 8. Вопросы, требующие подтверждения

1. Нужно ли хранить preview_url как обязательное поле или оно может быть NULL, если файл ещё не имеет миниатюры?
2. Должен ли duration храниться в секундах или лучше оставить строковый формат mm:ss и конвертировать на уровне чтения?
3. Использовать ли массив tags как text[] или хранить теги в отдельной таблице в будущем?
4. Какой bucket использовать для Supabase Storage: media, uploads или отдельные bucket для images/video/audio?
5. Нужно ли дополнительно хранить mime_type, hash файла или original_name для будущей проверки и синхронизации?
6. Нужно ли хранить store_path в виде relative path внутри bucket или полным объектным ключом?

---

## 9. Итог

Для первой версии Media Storage достаточно трёх таблиц и строгих RLS-правил:

- media_items — данные о файлах;
- collections — пользовательские подборки;
- collection_items — связи между подборкой и файлами.

Такая схема закрывает основные пользовательские сценарии, соответствует текущему frontend-моделям, поддерживает изоляцию данных и готова к переходу на Supabase Auth, Storage и REST API без лишней архитектурной сложности.
