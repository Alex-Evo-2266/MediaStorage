# Проектирование базы данных Media Storage

## 1. Область и ограничения

Frontend приложения подключён напрямую к Supabase; собственного backend-сервера в репозитории нет. В схеме используются три сущности:

- медиафайл;
- коллекция пользователя;
- связь между коллекцией и медиафайлом.

Текущие сценарии приложения:

- просмотр библиотеки файлов типов `image`, `video`, `audio`;
- создание пользовательских коллекций;
- добавление файла в коллекцию без дублирования;
- удаление файла из коллекции и удаление коллекции;
- изоляция данных разных пользователей.

Для backend выбран Supabase: PostgreSQL используется для метаданных, Supabase Auth — для идентификации пользователей, Supabase Storage — для бинарных файлов.

В базе данных хранятся метаданные и пути к объектам в Storage. Временные подписанные URL не сохраняются в таблицах: текущий клиент формирует их при чтении.

## 2. Сущности и соответствие frontend-модели

### 2.1. MediaItem

Текущая frontend-модель `MediaItem` содержит:

- `id`;
- `title`;
- `type`;
- `size`;
- `createdAt`;
- `previewUrl`;
- `duration` (опционально);
- `tags`.

В PostgreSQL эта сущность представлена таблицей `public.media_items`. При интеграции потребуется преобразование между именованием frontend в `camelCase` и PostgreSQL в `snake_case`. Например, `createdAt` соответствует `created_at`, а `duration` — `duration_seconds`.

`previewUrl` в frontend представляет собой временную ссылку, сформированную при чтении. База хранит `preview_path`, то есть путь к объекту превью в приватном bucket. Если превью отсутствует, `preview_path` может быть `NULL`; текущая загрузка не создаёт превью и записывает `NULL`.

### 2.2. MediaCollection

Текущая frontend-модель `MediaCollection` содержит:

- `id`;
- `name`;
- `description`;
- `mediaIds`.

В PostgreSQL коллекция хранится в `public.collections`. Массив `mediaIds` формируется при чтении коллекции на основе записей в `public.collection_items`, а не хранится в таблице `collections`.

### 2.3. Связь коллекции и файлов

Таблица `public.collection_items` реализует связь многие-ко-многим между коллекциями и медиафайлами. Первичный ключ состоит из пары `(collection_id, media_item_id)`, поэтому одна и та же запись о файле не может быть добавлена в одну коллекцию дважды.

## 3. Схема базы данных

### 3.1. Таблица `public.media_items`

Назначение:

- хранение метаданных файлов пользователя;
- привязка каждого файла к владельцу;
- фильтрация по типу, поиск по названию и тегам;
- хранение пути к оригинальному объекту и необязательного пути к превью в Supabase Storage.

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `id` | `uuid` | Первичный ключ, `DEFAULT gen_random_uuid()` |
| `owner_id` | `uuid` | Владелец; `NOT NULL`, внешний ключ на `auth.users(id)`, `ON DELETE CASCADE`, по умолчанию `auth.uid()` |
| `title` | `text` | Название; `NOT NULL`, строка после `trim` не должна быть пустой |
| `type` | `public.media_type` | `NOT NULL`; допустимые значения `image`, `video`, `audio` |
| `size` | `bigint` | Размер в байтах; `NOT NULL`, значение неотрицательное |
| `file_path` | `text` | Путь к оригиналу в bucket `media-files`; `NOT NULL`, уникальный, непустой |
| `preview_path` | `text` | Путь к превью в том же bucket; допускает `NULL`, если превью ещё нет |
| `duration_seconds` | `integer` | Длительность в секундах; допускает `NULL`, значение неотрицательное |
| `tags` | `text[]` | Массив тегов; `NOT NULL`, по умолчанию пустой массив |
| `created_at` | `timestamptz` | Время создания записи; `NOT NULL`, по умолчанию `now()` |

Пути `file_path` и `preview_path` должны начинаться с UUID владельца и `/`, например `<user-uuid>/<object-name>`. Это соглашение используется политиками Storage для ограничения доступа к объектам. В таблице `media_items` оно дополнительно проверяется ограничением.

`file_path` уникален во всей таблице. Это предотвращает привязку одного и того же пути к нескольким строкам.

### 3.2. Таблица `public.collections`

Назначение:

- хранение пользовательских подборок;
- привязка коллекции к владельцу;
- сортировка и поиск коллекций по имени и дате создания.

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `id` | `uuid` | Первичный ключ, `DEFAULT gen_random_uuid()` |
| `owner_id` | `uuid` | Владелец; `NOT NULL`, внешний ключ на `auth.users(id)`, `ON DELETE CASCADE`, по умолчанию `auth.uid()` |
| `name` | `text` | Название; `NOT NULL`, строка после `trim` не должна быть пустой |
| `description` | `text` | Описание; `NOT NULL`, по умолчанию пустая строка |
| `created_at` | `timestamptz` | Время создания; `NOT NULL`, по умолчанию `now()` |

### 3.3. Таблица `public.collection_items`

Назначение:

- хранение связей между коллекциями и медиафайлами;
- запрет повторного добавления одного файла в одну коллекцию;
- получение содержимого коллекции и списка коллекций, в которых используется файл.

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `collection_id` | `uuid` | `NOT NULL`, внешний ключ на `collections(id)`, `ON DELETE CASCADE` |
| `media_item_id` | `uuid` | `NOT NULL`, внешний ключ на `media_items(id)`, `ON DELETE CASCADE` |
| `created_at` | `timestamptz` | Время добавления; `NOT NULL`, по умолчанию `now()` |

Составной первичный ключ `(collection_id, media_item_id)` одновременно обеспечивает уникальность пары и не требует отдельного поля `id`.

## 4. Ограничения и индексы

### 4.1. `media_items`

Ограничения:

- `type` ограничен enum `image`, `video`, `audio`;
- `size >= 0`;
- `duration_seconds IS NULL OR duration_seconds >= 0`;
- `title` и `file_path` не могут быть пустыми строками;
- `preview_path` может быть `NULL`, но если задан, не может быть пустой строкой;
- `file_path` уникален;
- первый сегмент `file_path` и `preview_path` должен совпадать с `owner_id`.

Индексы:

- `(owner_id, created_at DESC)` — список файлов пользователя по дате;
- `(owner_id, type, created_at DESC)` — фильтрация по типу с сортировкой по дате;
- `(owner_id, title)` — поиск и сортировка по названию;
- `GIN(tags)` — операции поиска по массиву тегов.

### 4.2. `collections`

Ограничения:

- `name` не может быть пустым после `trim`;
- `description` может быть пустой строкой.

Индексы:

- `(owner_id, created_at DESC)` — список коллекций владельца по дате;
- `(owner_id, name)` — поиск и сортировка по названию.

### 4.3. `collection_items`

Ограничения и индексы:

- составной первичный ключ `(collection_id, media_item_id)` запрещает дубликаты;
- внешние ключи гарантируют существование коллекции и медиафайла;
- первичный ключ обеспечивает индекс для поиска по `collection_id`;
- отдельный индекс по `media_item_id` ускоряет поиск коллекций, содержащих файл.

При удалении коллекции или медиафайла связанные строки `collection_items` удаляются каскадно.

## 5. Стратегия Row Level Security (RLS)

RLS включается для всех трёх таблиц:

- `public.media_items`;
- `public.collections`;
- `public.collection_items`.

Frontend-проверки не считаются механизмом защиты: политики должны ограничивать доступ и при прямых запросах к Supabase API.

### 5.1. `media_items`

- `SELECT`: пользователь читает только строки, где `owner_id = auth.uid()`;
- `INSERT`: разрешено создание строки только с `owner_id = auth.uid()`;
- `UPDATE`: пользователь может изменять только собственные строки, а проверка `WITH CHECK` не позволяет сохранить строку с чужим владельцем;
- `DELETE`: разрешено удаление только собственных строк.

### 5.2. `collections`

- `SELECT`: доступны только коллекции текущего пользователя;
- `INSERT`: разрешено создание коллекций только с собственным `owner_id`;
- `UPDATE`: разрешено изменение только собственных коллекций;
- `DELETE`: разрешено удаление только собственных коллекций.

Для `owner_id` задан `DEFAULT auth.uid()`, однако клиент не должен считаться доверенным: RLS дополнительно проверяет владельца.

### 5.3. `collection_items`

- `SELECT`: связь доступна, только если коллекция принадлежит текущему пользователю;
- `INSERT`: разрешён, только если и коллекция, и медиафайл принадлежат текущему пользователю;
- `DELETE`: разрешён, только если коллекция принадлежит текущему пользователю;
- `UPDATE`: для MVP не предусмотрен.

Ограничения внешних ключей и RLS вместе предотвращают добавление чужого файла в свою коллекцию и добавление собственного файла в чужую коллекцию.

### 5.4. Supabase Storage

Используется приватный bucket `media-files`. Объекты должны размещаться по пути, начинающемуся с UUID пользователя: `<auth.uid()>/<object-name>`.

Политики `storage.objects` ограничивают чтение, загрузку, изменение и удаление объектов текущим владельцем и указанным bucket. Приватный bucket не предоставляет публичный доступ к файлам. Для отображения файла приложение должно использовать авторизованный запрос или временную подписанную ссылку.

Политики таблиц PostgreSQL и политики Storage — отдельные механизмы. Наличие RLS на `media_items` само по себе не защищает бинарные файлы.

## 6. Миграция

Миграция схемы находится в файле:

[`supabase/migrations/20261015_000001_create_media_storage_schema.sql`](../supabase/migrations/20261015_000001_create_media_storage_schema.sql)

Она включает:

- расширение `pgcrypto`, необходимое для `gen_random_uuid()`;
- создание enum `public.media_type`;
- создание таблиц `media_items`, `collections`, `collection_items`;
- ограничения `NOT NULL`, `CHECK`, `UNIQUE` и внешние ключи;
- индексы для выборок и фильтрации;
- включение RLS и политики доступа;
- создание приватного bucket `media-files`;
- политики доступа к объектам Storage;
- комментарии к таблицам.

Миграция существует в репозитории, но её применение к удалённому Supabase-проекту из исходников не подтверждается. Для применения через Supabase CLI необходимо:

1. Установить Supabase CLI и инициализировать конфигурацию проекта командой `supabase init`, если она ещё не создана.
2. Связать локальный проект с нужным Supabase-проектом согласно используемой конфигурации CLI.
3. Убедиться, что файл миграции находится в `supabase/migrations/` и имеет корректное имя.
4. Применить миграцию выбранным поддерживаемым способом, например через `supabase db push` для связанного проекта.

В текущем окружении Supabase CLI ранее не был установлен, а миграция не применялась и не проверялась на реальном Supabase-проекте. Поэтому её успешное выполнение пока не подтверждено. Перед применением следует выполнить проверку SQL и протестировать политики доступа.

## 7. Обоснование решений

1. **`owner_id` в пользовательских таблицах.** Это позволяет явно связывать данные с владельцем и реализовывать изоляцию через RLS.
2. **`collection_items` как отдельная таблица.** Это нормализованная модель связи многие-ко-многим, которая предотвращает дублирование и упрощает выборки.
3. **Файлы отдельно от метаданных.** Бинарные данные находятся в Supabase Storage, а PostgreSQL хранит метаданные и пути к объектам.
4. **Enum `media_type`.** Допускаются только типы `image`, `video`, `audio`.
5. **Длительность в секундах.** Числовое значение проще проверять и обрабатывать; формат `mm:ss` формируется на уровне frontend.
6. **Необязательный `preview_path`.** Запись о медиафайле может существовать до генерации превью.
7. **Приватный bucket.** Доступ к файлам ограничивается политиками Storage, а не только видимостью строк в таблице.

## 8. Решения и ограничения, которые нужно учитывать

- `tags` пока хранится как `text[]`. Отдельная таблица тегов не требуется для текущего MVP, но может понадобиться для расширенного управления тегами и связями.
- `mime_type`, контрольная сумма файла и исходное имя не включены в минимальную схему. Их стоит добавлять, если они понадобятся для проверки формата, обнаружения дубликатов или отображения исходного имени.
- Для `duration_seconds` frontend должен преобразовывать текущий формат длительности в число секунд и обратно.
- `preview_path` хранит путь в Storage, а не готовую публичную или подписанную ссылку.
- SQL-миграция создаёт bucket и политики Storage, но не реализует генерацию превью, серверные ограничения размера/MIME или каскадное удаление Storage-объектов при удалении строки `media_items`. Клиент реализует загрузку и удаление объекта перед удалением строки; эти раздельные операции могут завершиться частично.
- Проверка SQL статически не заменяет тестирование на реальном проекте Supabase.

## 9. Итог

Для первой версии Media Storage используются три таблицы:

- `media_items` — метаданные файлов;
- `collections` — пользовательские коллекции;
- `collection_items` — связи между коллекциями и файлами.

Supabase Auth идентифицирует пользователя, PostgreSQL хранит метаданные, RLS изолирует строки, а приватный Supabase Storage хранит бинарные файлы и ограничивает доступ к ним отдельными политиками.

Эта схема поддерживает текущие сценарии frontend с Supabase Auth, PostgreSQL и Storage. Перед развёртыванием необходимо сверить фактическую схему удалённого проекта с миграцией и проверить политики доступа в тестовом проекте. См. [документацию backend и интеграции](../backend_documentation.md).
