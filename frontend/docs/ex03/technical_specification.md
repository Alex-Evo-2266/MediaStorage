# Техническое задание — Media Storage

**Версия:** 1.0  
**Статус:** подготовлено для проверки перед разработкой  
**Тип проекта:** веб-приложение — домашний медиа-сервер

## 1. Описание проекта

### 1.1. Назначение

Media Storage — веб-приложение для централизованного хранения, просмотра и организации изображений, музыки и видео на домашнем сервере.

Пользователь получает доступ к медиатеке через браузер. Система позволяет загружать файлы, искать их, группировать по тегам и коллекциям, просматривать информацию о них и предоставлять доступ к медиаресурсам другим приложениям.

Одно из основных назначений проекта — интеграция с существующей домашней инфраструктурой. Например, система умного дома должна иметь возможность получать изображения для фона дашборда и использовать музыкальные файлы в сценариях автоматизации. Приложение MediaTagger должно иметь возможность обращаться к серверной медиатеке наряду с локальными файлами.

### 1.2. Проблема

Медиаконтент хранится на различных устройствах и носителях. Это затрудняет его поиск, организацию и использование в других системах.

Media Storage должен предоставить единое место хранения и унифицированный способ доступа к медиаресурсам, не требующий обязательного создания копий файлов для каждого приложения.

### 1.3. Основные задачи

- Организовать централизованное хранение медиаконтента.
- Предоставить веб-интерфейс для управления файлами.
- Обеспечить удобный поиск и группировку.
- Предоставить программный интерфейс для доступа к медиаресурсам.
- Обеспечить понятную обработку ошибок и отображение состояния операций.

### 1.4. Область MVP

В первую версию входят:
- просмотр изображений, музыки и видео;
- загрузка файлов;
- поиск, фильтрация и сортировка;
- просмотр сведений о файлах;
- создание и применение тегов;
- организация файлов по коллекциям;
- копирование ссылок на ресурсы;
- базовый API для получения медиаданных;
- отображение состояния хранилища;

Полноценное управление несколькими пользователями, расширенная система разрешений, автоматическое распознавание содержимого и сложная административная панель интеграций не входят в обязательный объём MVP и требуют отдельного согласования.

## 2. Целевая аудитория

### 2.1. Владелец домашнего медиасервера

Использует приложение для загрузки, просмотра и организации собственных изображений, музыкальных композиций и видео.

Основные потребности:
- быстро находить нужные файлы;
- загружать несколько файлов за одну операцию;
- организовывать медиатеку по тегам и коллекциям;
- получать ссылки на файлы;
- контролировать занятое дисковое пространство.

### 2.2. Пользователь интегрированных приложений

Использует медиаресурсы через другие приложения, например систему умного дома или MediaTagger.

Основные потребности:
- получать изображения и музыкальные файлы;
- обращаться к ресурсам по стабильному адресу или идентификатору;
- получать сведения о медиаконтенте через API.

### 2.3. Администратор медиасервера

Отвечает за настройки приложения и доступность хранилища.

В рамках MVP владелец и администратор могут быть одним пользователем.

## 3. Основные понятия

| Термин | Описание |
|---|---|
| Медиаресурс | Файл, сохранённый в Media Storage |
| Медиатека | Совокупность доступных медиаресурсов |
| Метаданные | Сведения о файле: название, формат, размер, дата добавления и другие доступные характеристики |
| Тег | Метка для классификации и поиска файлов |
| Коллекция | Группа медиаресурсов, объединённых пользователем |
| API | Программный интерфейс для взаимодействия с другими приложениями |
| Идентификатор ресурса | Уникальный идентификатор медиаресурса внутри системы |

## 4. Общие требования к интерфейсу

### 4.1. Структура

Интерфейс должен соответствовать выбранной UI-концепции Media Storage.

Основные элементы:
- боковая навигация;
- глобальный поиск;
- разделы «Обзор», «Изображения», «Музыка», «Видео»;
- разделы «Коллекции» и «Настройки»;
- область загрузки файлов;
- список или сетка медиаресурсов;
- информационная панель выбранного файла;
- индикатор использования дискового пространства.

### 4.2. Визуальное представление

Для изображений используются миниатюры, для видео — превью с длительностью при наличии соответствующих метаданных, для музыки — список композиций с названием и исполнителем при наличии этих данных.

Пользователь должен иметь возможность переключаться между сеточным и табличным представлением там, где это предусмотрено интерфейсом.

### 4.3. Общие состояния интерфейса

Для асинхронных операций необходимо предусмотреть:
- состояние загрузки;
- успешное завершение;
- отсутствие данных;
- отсутствие результатов поиска;
- ошибку выполнения;
- недоступность сервера.

Пользователь должен получать понятную обратную связь после выполнения действий.

**Дополнительно** - Страница настроек формируется в процессе. В процессе реализации приложения вносить в эту панель все необходимые данные для управления сервисом.

## 5. Функциональные требования

### FR-01. Просмотр медиатеки

**Приоритет:** Must have.

**Описание:** система должна отображать медиаресурсы, доступные пользователю.

**Требования:**
1. Система должна предоставлять отдельные разделы для изображений, музыки и видео.
2. Система должна отображать список файлов выбранной категории.
3. Карточка изображения должна содержать миниатюру, название, формат и размер.
4. Карточка видео должна содержать превью и длительность, если эти сведения доступны.
5. Запись музыкального файла должна содержать название и доступные сведения об исполнителе, формате, размере и длительности.
6. Пользователь должен иметь возможность открывать доступные медиаресурсы.
7. При отсутствии файлов система должна показывать пустое состояние с предложением загрузить контент.

**Результат:** пользователь видит актуальный список доступных медиаресурсов.

### FR-02. Загрузка файлов

**Приоритет:** Must have.

**Описание:** пользователь должен иметь возможность загружать медиаконтент с локального устройства на сервер.

**Требования:**
1. Загрузка должна запускаться через кнопку «Загрузить файлы».
2. Интерфейс должен позволять выбирать один или несколько файлов.
3. При наличии поддержки со стороны браузера должна быть доступна загрузка перетаскиванием файлов.
4. Перед загрузкой система должна проверять допустимые форматы и ограничения размера.
5. Система должна отображать очередь загрузки, названия файлов и состояние каждой операции.
6. Для выполняющихся операций необходимо отображать прогресс, если его можно определить.
7. После успешной загрузки файл должен становиться доступным в соответствующей категории медиатеки.
8. Ошибка загрузки одного файла не должна приводить к потере результатов других успешно завершённых загрузок.
9. Повторная попытка загрузки должна быть доступна для файлов, загрузка которых завершилась ошибкой.
10. Сервер должен повторно проверять допустимость формата и размера каждого файла независимо от проверок клиентского интерфейса.
11. Допустимые форматы и максимальный размер файла должны определяться согласованной конфигурацией приложения.
12. При отклонении файла сервер должен возвращать структурированную ошибку с кодом причины. Файл не должен появляться в медиатеке как успешно загруженный.
13. При загрузке нескольких файлов результат должен фиксироваться отдельно для каждого файла.
14. Повторная попытка должна быть доступна для неудачных операций без повторной загрузки файлов, которые уже были успешно сохранены.
15. После успешной загрузки файл должен оставаться доступным после перезапуска сервера.

**Результат:** файлы сохраняются в серверном хранилище и становятся доступны через интерфейс и API.

### FR-03. Поиск, фильтрация и сортировка

**Приоритет:** Must have.

**Описание:** система должна предоставлять средства поиска медиаресурсов.

**Требования:**
1. Глобальный поиск должен находить файлы по названию.
2. В рамках выбранной категории пользователь должен иметь возможность фильтровать файлы по поддерживаемым характеристикам.
3. Должны поддерживаться фильтрация по типу медиаконтента и тегам.
4. Пользователь должен иметь возможность сортировать список по дате добавления и названию.
5. При очистке поиска должны отображаться все элементы, соответствующие оставшимся фильтрам.
6. Если результаты отсутствуют, система должна показывать соответствующее сообщение.
7. Поиск и фильтрация не должны изменять сами файлы.
8. Поиск по названию должен находить файлы, содержащие введённую последовательность символов, а не только файлы с полным совпадением названия.
9. Поиск должен выполняться без учёта регистра символов.
10. Перед поиском система должна удалять пробелы в начале и конце поискового запроса.
11. При одновременном использовании нескольких фильтров файл должен отображаться только в том случае, если соответствует всем активным условиям.
12. Сортировка по названию должна быть стабильной; при одинаковых названиях порядок определяется дополнительным полем, согласованным в реализации.

**Результат:** пользователь может находить нужный контент без просмотра всей медиатеки.

### FR-04. Просмотр сведений о файле

**Приоритет:** Must have.

**Описание:** система должна предоставлять подробную информацию о выбранном медиаресурсе.

**Требования:**
1. При выборе файла должна открываться информационная панель или отдельная страница.
2. Система должна показывать название, тип, формат, размер и дату добавления.
3. При наличии метаданных должны отображаться разрешение изображения, длительность видео или аудиозаписи и другие релевантные сведения.
4. Система должна показывать назначенные теги и коллекции.
5. Пользователь должен иметь возможность скопировать ссылку на ресурс.
6. При недоступности файла система должна показывать сообщение об ошибке.
7. Если отдельные метаданные отсутствуют, система должна отображать остальные доступные сведения без подстановки вымышленных значений.
8. Если получение метаданных завершилось ошибкой, система должна сообщать о недоступности соответствующей информации.
9. Информация о тегах и коллекциях должна отражать актуальные сохранённые связи.
10. При запросе сведений об отсутствующем ресурсе система должна показывать сообщение о том, что ресурс не найден или недоступен.
11. При повторном открытии сведений о файле система должна получать актуальные данные, а не использовать устаревшие сведения без проверки.

**Результат:** пользователь получает необходимые сведения о файле и доступные действия.

### FR-05. Управление тегами

**Приоритет:** Must have.

**Описание:** пользователь должен иметь возможность классифицировать файлы с помощью тегов.

**Требования:**
1. Пользователь должен иметь возможность создавать теги.
2. Пользователь должен иметь возможность назначать файлу один или несколько тегов.
3. Пользователь должен иметь возможность удалять назначенные теги.
4. Поиск и фильтрация по тегу должны возвращать соответствующие медиаресурсы.
5. Названия тегов должны проходить проверку на пустое значение.
6. Удаление назначения тега у файла не должно удалять сам медиаресурс.
7. Название тега не может быть пустым или состоять только из пробелов.
8. Правила обработки повторяющихся названий тегов должны быть определены явно.
9. Удаление назначения тега у файла не должно удалять сам тег из системы.
10. Поведение при удалении тега, назначенного нескольким файлам, должно быть определено явно.

**Результат:** файлы можно классифицировать и находить по пользовательским меткам.

### FR-06. Управление коллекциями

**Приоритет:** Must have.

**Описание:** пользователь должен иметь возможность группировать медиаресурсы в коллекции.

**Требования:**
1. Пользователь должен иметь возможность создавать коллекции.
2. Пользователь должен иметь возможность добавлять медиаресурсы в коллекции и удалять их оттуда.
3. Система должна отображать название коллекции и количество входящих в неё файлов.
4. При открытии коллекции система должна показывать входящие в неё медиаресурсы.
5. Один файл должен иметь возможность входить в несколько коллекций.
6. Удаление файла из коллекции не должно удалять сам файл.
7. Название коллекции не должно быть пустым.
8. Название коллекции не может быть пустым или состоять только из пробелов.
9. Правила обработки повторяющихся названий коллекций должны быть определены явно.
10. Поведение при удалении коллекции не должно приводить к удалению входящих в неё файлов.
11. Если переименование коллекций входит в MVP, оно должно быть описано как отдельная операция с критериями приёмки

**Результат:** пользователь организует медиатеку по темам, событиям и другим признакам.

### FR-07. Получение ссылки на медиаресурс

**Приоритет:** Must have.

**Описание:** система должна предоставлять способ получения адреса отдельного медиаресурса.

**Требования:**
1. В интерфейсе сведений о файле должна присутствовать кнопка «Копировать ссылку».
2. Система должна формировать адрес, соответствующий принятой модели доступа к медиаресурсам.
3. Адрес должен однозначно определять нужный ресурс.
4. Система должна сообщать об успешном копировании или ошибке.
5. Доступ к ресурсу должен соответствовать настроенным правилам авторизации.
6. Наличие ссылки не должно автоматически предоставлять неограниченный публичный доступ к защищённому содержимому.
7. Для получения содержимого большого медиаресурса система должна поддерживать выдачу временной подписанной ссылки, позволяющей получить файл напрямую по HTTP без передачи всего содержимого через API-обработчик метаданных.
8. Перед выдачей ссылки система должна проверить JWT и право запрашивающего субъекта на доступ к указанному медиаресурсу.
9. Подписанная ссылка должна быть ограничена конкретным медиаресурсом, разрешённой операцией и сроком действия.
10. Истечение срока действия ссылки должно приводить к отказу в доступе. Для повторного получения файла клиент должен запросить новую ссылку.
11. Секрет или закрытый ключ, используемый для подписания ссылок, не должен передаваться клиентам.
12. Временная подписанная ссылка должна рассматриваться как секрет доступа: её нельзя включать в открытые журналы, сообщения об ошибках или публичные данные API.

**Результат:** пользователь может использовать адрес ресурса в совместимых приложениях.

### FR-08. API для интеграций

**Приоритет:** Must have.

**Описание:** система должна предоставлять программный интерфейс для получения списка медиаресурсов, их метаданных и содержимого.
API Media Storage предназначен для получения метаданных, поиска медиаресурсов и управления операциями, предусмотренными контрактом API. Получение содержимого больших файлов может выполняться по временным подписанным ссылкам, выдаваемым после проверки прав доступа.

Защищённые операции API должны принимать JWT, выданный отдельным сервисом авторизации. Media Storage должен проверять подпись токена с использованием открытого ключа сервиса авторизации, а также проверять срок действия, издателя, получателя и необходимые права доступа.

Проверка JWT должна выполняться на стороне Media Storage без обязательного обращения к сервису авторизации при каждом запросе. Контракт взаимодействия с сервисом авторизации должен определять формат токенов, используемый алгоритм подписи, идентификатор ключа и порядок получения и обновления открытых ключей.

**Требования:**
1. API должен позволять получать список доступных медиаресурсов.
2. API должен поддерживать получение сведений об отдельном ресурсе по идентификатору.
3. API должен предоставлять способ получения содержимого файла.
4. API должен поддерживать получение ресурсов с учётом категории и предусмотренных фильтров.
5. Ответы API должны иметь документированный формат.
6. Ошибки должны возвращаться с соответствующими HTTP-статусами и понятной структурой ответа.
7. API должен проверять необходимые права доступа.
8. Адреса ресурсов должны быть пригодны для использования совместимыми клиентами.
9. API должен различать отсутствие действительных учётных данных и отсутствие необходимых прав доступа.
10. API должен предоставлять способ получения временной подписанной ссылки на содержимое медиаресурса после проверки прав доступа.
11. Для получения списка медиаресурсов и метаданных должен использоваться документированный формат JSON.
12. Контракт API должен определять методы и маршруты, параметры запросов, формат успешных ответов, схему ошибок, HTTP-статусы, правила пагинации и требования к авторизации.
13. Клиенты не должны получать прямой доступ к внутренней файловой системе или базе данных Media Storage.

**Предполагаемые потребители:**
- система умного дома — получение изображений и музыкальных ресурсов;
- MediaTagger — получение серверных файлов и метаданных;
- другие приложения, которым требуется доступ к медиатеке.

**Результат:** внешние системы могут использовать медиаресурсы без обязательного создания отдельных копий.

### 5.8.1. Контракт API

До реализации API должна быть подготовлена и согласована спецификация конечных точек.

Для каждой операции необходимо определить:

- HTTP-метод и маршрут;
- назначение операции;
- обязательные и необязательные параметры;
- формат запроса и ответа;
- правила пагинации и фильтрации, если они применяются;
- требования к авторизации;
- возможные HTTP-статусы;
- структуру ошибки и стабильный код причины.

API должен обеспечивать получение списка медиаресурсов, сведений об отдельном ресурсе и его содержимого. Идентификатор ресурса должен однозначно определять запись в пределах системы.

Неавторизованный запрос к защищённому ресурсу должен завершаться отказом без передачи содержимого файла. Запрос к отсутствующему ресурсу должен возвращать документированный ответ.

Спецификация должна быть достаточной для создания и тестирования клиента без необходимости изучать внутреннюю реализацию сервера.

### FR-09. Состояние хранилища

**Приоритет:** Should have.

**Описание:** система должна отображать сведения о заполненности хранилища.

**Требования:**
1. На странице обзора или в боковой панели должно отображаться занятое дисковое пространство.
2. При наличии соответствующих данных должно отображаться общее и свободное пространство.
3. Значения должны поступать из достоверного источника, а не задаваться как постоянные демонстрационные числа.
4. При невозможности получить сведения система должна отображать состояние недоступности данных.

**Результат:** пользователь может контролировать использование хранилища.

### FR-10. Работа с интеграциями

**Приоритет:** Nice to have для отдельного пользовательского раздела.

**Описание:** интерфейс может предоставлять обзор возможностей интеграции с внешними приложениями.

**Требования:**
1. При наличии реализованных подключений система должна отображать актуальные сведения о них.
2. Интерфейс должен позволять просматривать документацию API.
3. Если подключение требует дополнительных настроек, система должна показывать соответствующие инструкции.
4. Состояние подключения должно отражать реальные данные, а не фиктивный статус.

**Результат:** пользователь получает информацию о подключённых приложениях и способах интеграции.

## 6. Нефункциональные требования

### NFR-01. Удобство использования

- Интерфейс должен соответствовать выбранной UI-концепции.
- Основные разделы должны быть доступны из боковой навигации.
- Ключевые действия должны иметь понятные названия.
- Длительные операции должны сопровождаться визуальной обратной связью.
- Интерфейс должен корректно отображать пустые состояния и ошибки.
- Пользователь не должен терять доступ к основным действиям при отсутствии файлов.

### NFR-02. Производительность

- Списки файлов должны загружаться без необходимости передавать содержимое всех файлов.
- Для изображений и видео следует использовать миниатюры, если они предусмотрены реализацией.
- При большом количестве файлов следует предусмотреть постраничную загрузку или другой механизм ограничения объёма выдачи.
- Поиск и фильтрация должны оставаться работоспособными при росте медиатеки.
- Загрузка крупных файлов не должна требовать повторной загрузки всей страницы после каждого завершения операции.

Конкретные целевые показатели времени отклика и максимального количества файлов определяются после выбора архитектуры и оборудования.

### NFR-03. Безопасность

- Доступ к API и защищённым файлам должен контролироваться.
- Сервер должен проверять тип, размер и допустимость загружаемых файлов.
- Имя файла не должно использоваться для обхода каталога хранения или доступа к произвольным файлам сервера.
- Ошибки сервера не должны раскрывать внутренние пути, секреты или конфигурационные данные.
- Секреты доступа к API не должны храниться в открытом виде в клиентском коде.
- При использовании удалённого доступа следует предусмотреть защищённое соединение.
- Если используется авторизация, сервер должен проверять её на каждой защищённой операции.
- Доступ к защищённому файлу должен проверяться сервером при каждом запросе содержимого, в том числе при обращении по прямому URL.
- Знание идентификатора ресурса или его URL не заменяет проверку прав доступа.
- Способ авторизации пользователей и внешних приложений должен быть согласован до реализации API.
- Для каждой защищённой операции необходимо определить ожидаемое поведение при отсутствии авторизации и недостаточных правах.
- Если будут использоваться временные ссылки, должны быть определены срок их действия, правила проверки и порядок отзыва доступа.
- Ошибки авторизации не должны раскрывать содержимое защищённых файлов или внутренние сведения сервера.
- JWT должен проверяться локально с использованием открытого ключа, соответствующего ключу подписи сервиса авторизации.
- Сервис должен проверять подпись JWT, разрешённый алгоритм, издателя, получателя и временные ограничения токена.
- Доступ к каждой защищённой операции должен предоставляться только при наличии необходимых прав.
- Закрытый ключ сервиса авторизации не должен передаваться Media Storage или другим проверяющим сервисам.
- Ключи подписи временных ссылок должны храниться отдельно от ключей сервиса авторизации.
- Время жизни подписанных ссылок должно быть ограничено и задаваться конфигурацией системы.
- JWT, секреты и полные подписанные ссылки не должны попадать в журналы в открытом виде.
- При ротации ключей система должна обеспечивать переход на новые ключи без необоснованного раскрытия доступа.
- При удалённом доступе к API и файлам должен использоваться HTTPS.

### NFR-04. Надёжность хранения

- Успешно завершённая загрузка должна подтверждаться только после сохранения файла и необходимых метаданных.
- При ошибке сохранения система не должна отображать файл как успешно загруженный.
- Ошибка обработки одного файла не должна автоматически приводить к удалению других корректно сохранённых файлов.
- Поведение системы при перезапуске сервера должно определяться выбранным механизмом хранения и восстановления данных.
- Резервное копирование и восстановление должны быть предусмотрены в дальнейшей архитектуре, если они не входят в MVP.

### NFR-05. Совместимость

- Веб-интерфейс должен поддерживать актуальные версии распространённых настольных браузеров.
- Интерфейс должен адаптироваться к доступной ширине экрана.
- API должен использовать документированные форматы запросов и ответов.
- При разработке интеграций необходимо учитывать, что разные клиенты могут иметь различные требования к авторизации и способам получения файлов.

### NFR-06. Сопровождаемость

- Код должен быть разделён на логические компоненты.
- Логика хранения файлов должна быть отделена от логики пользовательского интерфейса.
- API должен иметь документацию по доступным операциям и форматам ответов.
- Ошибки операций должны фиксироваться средствами журналирования без записи секретов.
- Изменения требований должны сопровождаться обновлением документации.

| Код | Ситуация | Поведение системы |
|---|---|---|
| ERR-01 | Недопустимый формат файла | Отклонить файл и показать причину |
| ERR-02 | Превышен лимит размера | Сообщить об ограничении и не начинать загрузку |
| ERR-03 | Нет свободного места | Прекратить загрузку, если сохранение невозможно, и уведомить пользователя |
| ERR-04 | Потеря соединения | Показать ошибку и предоставить возможность повторной попытки |
| ERR-05 | Ошибка сохранения файла | Не сообщать об успехе; показать ошибку |
| ERR-06 | Пустой результат поиска | Показать сообщение и предложить изменить запрос |
| ERR-07 | Медиатека пуста | Показать пустое состояние и кнопку загрузки |
| ERR-08 | Некорректный тег или название коллекции | Подсветить поле и объяснить причину |
| ERR-09 | Файл отсутствует | Вернуть сообщение о недоступности ресурса |
| ERR-10 | Нет авторизации | Отклонить запрос к защищённому ресурсу |

| ERR-13 | Ошибка получения дисковой статистики | Показать состояние недоступности данных |

### Общие правила обработки ошибок

1. Сообщения должны быть понятны пользователю и не содержать внутренних трассировок или секретов.
2. Ошибки валидации должны по возможности отображаться рядом с соответствующими элементами интерфейса.
3. Для временных ошибок необходимо предусмотреть повтор операции, если он безопасен.
4. При повторной загрузке система должна избегать случайного создания дубликатов, если для этого предусмотрен механизм идентификации загрузки.
5. При отсутствии данных следует показывать пустое состояние, а не сообщение о технической ошибке.
6. При ошибках доступа сервер не должен возвращать содержимое защищённого файла.

## 8. Основные критерии готовности MVP

MVP считается реализованным, если:

- пользователь может просматривать изображения, музыку и видео;
- пользователь может загружать поддерживаемые файлы;
- загруженные файлы появляются в медиатеке;
- поиск, фильтрация и сортировка работают согласно требованиям;
- пользователь может просматривать сведения о файлах;
- теги и коллекции позволяют организовывать медиаконтент;
- пользователь может получить ссылку на ресурс;
- внешний клиент может получить доступ к медиаресурсу через документированный API с учётом прав доступа;
- предусмотрены состояния загрузки, пустые состояния и обработка основных ошибок;
- приложение корректно отображает доступную информацию о хранилище.

Приёмка выполняется по тест-кейсам AT-01—AT-24. Тест считается пройденным, если все указанные проверки результата и состояния данных выполнены. Изменить сохранённые связи с тегами/коллекциями и открыть сведения повторно. | Отображаются название, тип, формат, размер, дата добавления и доступные дополнительные метаданные. Отсутствующие значения не подменяются вымышленными. После изменения связей отображаются актуальные теги и коллекции. |
| AT-14 | FR-04 / ERR-09: отсутствующий файл | Удалить тестовый файл непосредственно из тестового хранилища, оставив запись о ресурсе, если архитектура допускает такое состояние. Запросить его сведения и содержимое. | Система сообщает, что ресурс недоступен или не найден; не показывает ложный успешный результат и не раскрывает внутренний путь хранения. |
| AT-15 | FR-05: создание и назначение тегов | Создать тег `Отпуск`, назначить его двум файлам, выполнить поиск по тегу, затем снять назначение с одного файла. | Оба файла находятся по тегу до снятия назначения. После снятия назначения один файл перестаёт соответствовать фильтру, второй остаётся. Сами файлы не удаляются, тег остаётся в системе. |
| AT-16 | FR-05 / ERR-08: пустой и повторяющийся тег | Попытаться создать тег из пустой строки и строки из пробелов; затем повторно создать тег с уже существующим названием. | Пустые названия отклоняются с сообщением у поля. Повторяющееся название обрабатывается строго по согласованному правилу (например, отказ с сообщением или использование существующего тега); дубли не создаются вопреки этому правилу. |
| AT-17 | FR-06: создание и использование коллекции | Создать коллекцию `Поездка`, добавить в неё два файла, открыть коллекцию и проверить счётчик. Удалить один файл из коллекции. | Коллекция показывает два файла и корректный счётчик; после удаления связи — один файл и счётчик 1. Удаление файла из коллекции не удаляет сам файл из медиатеки. |
| AT-18 | FR-06 / ERR-08: пустая и повторяющаяся коллекция | Попытаться создать коллекцию с пустым названием и названием из пробелов; повторить создание уже существующего названия. | Пустые названия отклоняются. Повторяющиеся названия обрабатываются по согласованному правилу, без непредусмотренных дубликатов. Удаление коллекции, если поддерживается, не удаляет входящие в неё файлы. |
| AT-19 | FR-07: копирование ссылки | Открыть сведения о доступном файле и нажать «Копировать ссылку». Интерфейс сообщает об успехе либо об ошибке копирования. При разрешённом доступе ссылка открывает нужный ресурс, а не другой файл. |

Повторить запрос по прямому URL/идентификатору. | Неавторизованный запрос получает согласованный статус отказа (обычно HTTP 401), запрос без нужных прав — согласованный статус запрета (обычно HTTP 403), разрешённый запрос получает содержимое. Затем передать несуществующий ID и некорректные параметры. | Успешные запросы возвращают ответы согласованной схемы. Отсутствующий ресурс возвращает документированный статус (обычно HTTP 404). | AT-22 | FR-08 / ERR-12: недоступность API | В тестовой среде сделать сервис недоступным либо смоделировать серверную ошибку и выполнить запрос клиентом. | Клиент показывает состояние ошибки/недоступности и не отображает несуществующий успешный результат. Ошибка соответствует документированному формату, если ответ сервера доступен; после восстановления сервиса запрос можно выполнить повторно. |
| AT-23 | FR-09 / ERR-13: состояние хранилища | Сравнить отображаемые показатели с показателями выбранного источника данных на сервере. При ошибке интерфейс явно сообщает о недоступности статистики, а не показывает нулевые значения как достоверные. |
| AT-24 | Общая обработка ошибок / NFR-01 | Проверить ошибки загрузки, валидации, доступа и API. Просмотреть сообщения интерфейса и ответы сервера. | Пользователь получает понятное сообщение и доступную следующую операцию, если повтор безопасен. В пользовательских сообщениях и API-ответах отсутствуют трассировки, секреты и внутренние пути. Ошибка одной операции не стирает результаты ранее успешно завершённых операций. |

#### Правила выполнения и фиксации результатов

1. Для каждого тест-кейса записывать фактический результат, статус «Пройден / Не пройден», дату проверки и обнаруженные дефекты.
2. Проверять не только сообщение в интерфейсе, но и фактическое состояние данных: наличие или отсутствие записи о ресурсе, сохранность файла и связи с тегами/коллекциями.
3. Сбои диска, сети и авторизации моделировать в тестовой среде, не повреждая рабочую медиатеку.
4. До начала приёмки зафиксировать допустимые форматы, максимальный размер, правила дубликатов тегов/коллекций, направления сортировки, модель авторизации и точные HTTP-статусы API. В тестах AT-16, AT-18, AT-20 и AT-21 проверять именно утверждённые решения.
5. Количественные критерии производительности и список поддерживаемых браузеров должны быть согласованы до проведения соответствующих испытаний. Эти проверки не считаются завершёнными только на основании качественных формулировок NFR-02 и NFR-05.

## 9. Ограничения и вопросы для уточнения

До начала полноценной разработки необходимо согласовать следующие параметры:

1. **Авторизация:** будет ли сервер доступен только в домашней сети или также через интернет? Нужна ли поддержка нескольких пользователей?
2. **Файловое хранилище:** какие форматы и максимальные размеры файлов будут разрешены?
3. **Дубликаты:** допускается ли хранение одинаковых файлов и как система должна их определять?
4. **Метаданные:** какие сведения следует извлекать автоматически из изображений, аудиозаписей и видео?
5. **API:** какие именно операции нужны системе умного дома и MediaTagger в первой версии?
6. **Ссылки:** должны ли адреса работать только в домашней сети или также при удалённом доступе?
7. **Удаление:** требуется ли корзина и возможность восстановления удалённых файлов?
8. **Производительность:** каковы предполагаемый объём медиатеки и количество одновременных клиентов?
9. **Архитектура:** какие технологии и способ хранения данных должны использоваться?

Ответы на эти вопросы должны быть зафиксированы до реализации соответствующих функций. Если решение не согласовано, AI-агент должен явно указать неопределённость и запросить уточнение, а не самостоятельно вводить критически важные ограничения.

## 10. Инструкция для AI-агента-разработчика

При реализации проекта необходимо:

1. Использовать этот документ как основу функциональных и нефункциональных требований.
2. Перед началом разработки изучить существующую структуру проекта и используемые технологии.
3. Сопоставить требования с существующим кодом и определить недостающие компоненты.
4. Разбить реализацию на небольшие этапы, начиная с основных функций MVP.
5. Не реализовывать фиктивные действия и демонстрационные данные вместо работающей функциональности.
6. Для каждой функции подготовить проверяемые критерии готовности.
7. Обрабатывать ошибки на клиенте и сервере в соответствии с разделом 7.
8. Не принимать необоснованных архитектурных решений по вопросам, перечисленным в разделе 9.
9. После каждого этапа запускать доступные проверки и сообщать о результатах.
10. По завершении провести ревью соответствия реализации этому техническому заданию и перечислить невыполненные требования.
