# ДЗ5 — Шаг 1. Проектирование базы данных Media Storage

## Role — Роль

Ты — опытный backend-разработчик и архитектор PostgreSQL/Supabase, специализирующийся на проектировании реляционных баз данных, SQL-миграциях и Row Level Security (RLS).

## Context — Контекст

Проект Media Storage — frontend-приложение на React, TypeScript, Vite и Material UI для организации домашней медиатеки.

Сейчас приложение использует mock-данные и локальное React-состояние. Необходимо подготовить переход к Supabase: PostgreSQL, Supabase Auth, Supabase Storage и REST API.

Основные функции:
- просмотр и поиск изображений, видео и аудио;
- получение информации о медиафайлах;
- загрузка и удаление файлов;
- создание и удаление коллекций;
- добавление файлов в коллекции и удаление файлов из них;
- изоляция пользовательских данных.

## Task — Задача

Проанализируй существующий проект и подготовь проект базы данных для первой версии Media Storage.

### Этап 2. Проектирование схемы

Рассмотри следующие таблицы:
- `media_items` — метаданные медиафайлов;
- `collections` — пользовательские коллекции;
- `collection_items` — связи между коллекциями и медиафайлами.

Используй `auth.users` Supabase Auth для идентификации пользователей. Не создавай собственную таблицу паролей.

Определи для каждой таблицы:
- назначение;
- поля и типы PostgreSQL;
- первичный ключ;
- внешние ключи;
- ограничения NOT NULL, UNIQUE и CHECK;
- значения по умолчанию;
- индексы, необходимые для поиска и фильтрации.

Учти требования:
- типы файлов: `image`, `video`, `audio`;
- размер хранится в байтах;
- метаданные и путь к файлу хранятся в PostgreSQL, а бинарные файлы — в Supabase Storage;
- у каждой пользовательской записи есть владелец;
- одна коллекция может содержать несколько файлов, а один файл может входить в несколько коллекций;
- повторное добавление одного файла в одну коллекцию запрещено;
- пользователь не должен получать доступ к чужим записям.

Не добавляй таблицы, поля и подсистемы, которые не нужны текущему MVP, без обоснования.

### Этап 3. Безопасность

Опиши стратегию RLS для всех трёх таблиц:
- включение RLS;
- чтение только собственных записей;
- создание записей от имени текущего пользователя;
- изменение и удаление только собственных записей;
- проверка владельца медиафайла при добавлении в коллекцию.

Не считай проверку только на frontend достаточной защитой. Учитывай, что политика доступа должна действовать и при прямых REST-запросах.

### Этап 4. Миграции

Миграция должна содержать создание таблиц, ограничений, индексов, включение RLS и необходимые политики доступа.

Не выполняй миграцию в удалённом проекте и не используй секреты. Если в репозитории ещё не настроен Supabase CLI, подготовь SQL-файл и укажи, что требуется для его применения.

### Этап 5. Документация

Создай документ `docs/database_design.md`, содержащий:

## 📌 Что соответствует текущему проекту

По фактической модели приложения:

- `MediaItem` содержит: `id`, `title`, `type`, `size`, `createdAt`, `previewUrl`, `duration?`, `tags`;
- `MediaCollection` содержит: `id`, `name`, `description`, `mediaIds`;
- коллекции в текущей логике — это набор ссылок на файлы, а не отдельное хранение массива в реляционной форме;
- в реляционной схеме это корректно выражено через отдельную таблицу `collection_items` с уникальным ограничением на пару `(collection_id, media_item_id)`, чтобы запретить повторное добавление файла в одну коллекцию.

---

## 🔐 RLS и безопасность

Для всех трёх таблиц предусмотрена политика на уровне PostgreSQL:

- чтение только своих записей;
- создание только с `owner_id = auth.uid()`;
- изменение и удаление только собственных строк;
- при добавлении в коллекцию проверяется, что:
  - коллекция принадлежит текущему пользователю;
  - медиафайл тоже принадлежит текущему пользователю.

Это защищает даже при прямых REST/SQL-запросах, а не только на frontend.
